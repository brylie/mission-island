# Mission Island architecture

**Status:** The physics section is verified by [the broadphase tests](../test/broadphase.test.mjs). Type: reference. Last tended 2026-11-26. Older sections predate the [knowledge framework](knowledge-framework.md).

The LAN host owns gameplay state, including movement, crew membership, orders, the shared bank, and saved progress. The game client renders host snapshots and sends player input. The Workbench and Saltwind preview run local sessions and can reuse mechanics and assets.

## Where changes belong

| Area | Responsibility |
| --- | --- |
| [Host simulation](../server/game.ts) | Sequences each tick, routes typed crew commands, and exposes snapshots. Crew reservations, purchases and payouts, held equipment, and interactions live in their feature modules under `server/`. |
| [Host adapters](../server/multiplayer.ts) | Vite wiring, LAN invite and bank endpoints, timers, and save scheduling. [Socket sessions](../server/socket-sessions.ts) handle WebSocket framing, timeouts, and snapshot backpressure. [Save storage](../server/save.ts) handles file I/O, validation, and migration. |
| [Shared simulation](../src/simulation/) | Movement, fishing, [ridge flight](../src/simulation/ridge-flight.ts) and Cannon physics that can run on the host or in a browser preview. Keep these modules independent of DOM, Babylon, and host adapters. |
| [World data](../src/worlds/) | Island-specific placements, routes, and terrain profiles live in the [Starter](../src/worlds/starter/layout/) and [Saltwind](../src/worlds/saltwind/layout/) layouts. World and terrain modules resolve feature anchors and sample those layouts for walking, cargo, rendering, and the Saltwind tour. |
| [Assets](../src/assets/) | Reusable procedural models and their poses. Add models alongside their asset family, such as crew, buildings, flatbed, props, routes, or waterfront. Keep placement coordinates with the world that uses the model. Keep source meshes, textures and audio with their asset family and import them through Vite. Use `public/` for files that require a stable, unprocessed URL. |
| [Shared geometry](../src/assets/geometry/) | Model-local dimensions, support volumes, and surface profiles shared by rendering and gameplay. Group the data by asset family and give each prop definition its own support boxes. A placed prop references that definition. Keep these modules dependency-free so the host can read the same definitions as the renderer. |
| [Audio](../src/audio/) | Procedural sound. Recipes, gait, surface, shore and mix rules are pure modules that run under Node tests. A [recipe worker](../src/audio/recipe-worker.ts) renders buffers off the UI thread, and every footstep, crate and current surf variant is rendered once audio unlocks. The engine owns the Web Audio context, its gesture and visibility lifecycle, the buffer cache and voice budgets. Host physics reports crate contacts as `crate-impact` crew notices with unique IDs; surf, footsteps, the flatbed engine, wind, plant contact and birds are rendered from each browser's own view of shared state. Wind follows one gust envelope in `src/wind.ts` that the windblown particles also use, and gull calls follow the same flight functions as the visible gulls, timed from the island clock so both browsers hear them together. Nothing audible is saved. |
| [Presentation](../src/scene.ts) | The game, Workbench, and Saltwind entry points wire browser input, views and rendering. Keep components and preview studies in feature modules. The [Workbench catalog](../src/workbench/catalog.ts) assembles studies in display order. |

## How to add a feature

Use the [Game Architect skill](../.agents/skills/mission-island-game-architect/SKILL.md) to trace a feature through its owners, decide what is worth sharing, and review the co-op and save behavior it depends on.

- Give each module a specific responsibility and a small public interface. Keep an entry point focused on composition. When a feature adds substantial branching, state or lifecycle code, put it in the owning feature module and pass only the state or callbacks it needs.
- Keep tick order and transaction boundaries visible. A change to command timing, a checkpoint, or the order of movement, equipment, and physics can affect play and reconnects. Cover those cases through the host integration tests.
- Share browser-safe rules through feature modules. Keep protocol changes focused on fields that cross the connection. Treat saved records and public Workbench subject IDs as compatibility contracts. Update validation and migration tests when a saved format changes.
- Organize world changes by island and by site, region, or system as the content grows. Give placements stable IDs, and record which geometry affects walking, cargo, or navigation. Aim to feed render and collision builders from the same placement data. When geometry depends on shared progress, such as Wren's gate leaf or the ferry barrier and deck, derive the solids from the snapshot in one rules module. The host places the matching physics bodies each tick, and walking reads the same solids as an extra surface. Keep Babylon mesh construction and batching in the presentation layer.
- Keep live-only shared state out of the save. [Crew marks](mechanics/fire-watch.md#binoculars-and-crew-marks) ride in every snapshot as `marks`, but `saveIsland` in [island state](../server/island-state.ts) picks world fields by name, so they never reach the save, and `restoreIsland` starts them empty. Tie such state to the crewmate who owns it and drop it when they disconnect, because crew slots are reused. Keep it off `Player`, which is saved.
- Add regression cases to the matching `test/game-*.test.mjs` suite. The [game test harness](../test/support/game-harness.mjs) supplies fake sockets, an injected clock, and save fixtures. Use the smallest suite that exercises the feature's actual entry point.

### Where numeric values belong

- Keep gameplay thresholds, timing, and tolerances as named constants in the module that owns the rule. Share a constant when its callers rely on the same contract, such as the motion limit used by a prompt and its host check.
- Keep dimensions, support boxes, and attachment points together in the model's geometry. A world layout places that model at a site. Rendering, walking, and cargo can then read the same dimensions wherever they describe the same surface.
- Keep authored shader, sound, and effect settings in the approved data modules. Workbench subjects import the production model, recipe, or attachment data and supply the camera, initial state, and replay settings for the study.

The [numeric lint policy](../CONTRIBUTING.md#quality-checks) lists the allowed data locations and the rules ESLint enforces.

## Composing behavior with traits

A trait is a capability or characteristic described by a small, typed piece of data. An entity definition combines the traits that apply to it. A shared system reads each trait and implements its behavior. Add traits when they describe behavior that multiple entities can use, or when an optional capability needs a clear owner.

| Responsibility | Where it belongs |
| --- | --- |
| Definition | Keep reusable tuning and geometry with the entity family. A trait can describe drive parameters, a threat detection range, or a plant's moisture requirements. |
| Behavior | Keep the rules in the system that uses the trait. Shared mechanics can run on the host and in the Workbench. The host owns changes that affect multiplayer gameplay. |
| Instance state | Give placed entities stable IDs when gameplay needs to refer to them. Keep changing values, such as speed or remaining forage, with the instance. Send or save the values that clients need to render or that a restart must restore. |
| Appearance and placement | Keep models and visual effects in the asset and presentation layers. Keep each island's spawn points, habitats, and placements with its world data. Share physical attachment points between simulation and rendering when they need to line up. |

### Flatbed, learner vehicles and future fire truck

The [flatbed's ground-drive definition](../src/vehicles/flatbed.ts) holds its wheel layout, suspension, throttle, steering, and brake tuning. The [driving system](../src/simulation/ground-drive.ts) uses that definition with a chassis body and a terrain height query. The [flatbed model](../src/assets/flatbed.ts) uses the same wheel dimensions to build and animate its wheels. The current system steers the front axle and drives the rear axle. Road vehicle models take their wheels, profile bodywork, part merging and fleet trim paint (chassis, glass, lamps, bumpers) from the [shared vehicle kit](../src/assets/vehicle-kit.ts). Its paint roles and wheel proportions live in [its data module](../src/assets/geometry/vehicle-kit.ts). Each model still places its own glass and lamps. Each vehicle keeps its own body paint, silhouette and gameplay dimensions, so a new vehicle, such as the fire truck, joins the same fleet by using the kit.

| Vehicle | Shared traits | Equipment |
| --- | --- | --- |
| Flatbed | Ground drive and seats with the flatbed's current wheel layout, suspension, braking, and seat positions | A cargo bed with load slots and support surfaces |
| Learner vehicles | The [Fire and Rescue pickup and Island Farm tractor](../src/learner-vehicles.ts) share the ground drive with their own [tuning](../src/vehicles/learner-drives.ts), colliders, seats and exits | Practice stops that pay career driving XP |
| Future fire truck | The same throttle, steering, brake, and boarding rules with its own chassis dimensions, suspension, and seat positions | A pump and hose station so one crewmate can drive while the other operates the hose |

Keep the models in the asset layer. Let island data choose where each vehicle spawns: the learner vehicles park at the places in the [Starter Island layout](../src/worlds/starter/layout/places.ts). The tractor's practice stops are listed there too; the pickup's [rescue tour](../src/rescue-tour.ts) reads its stops from the fire stations, the farm's delivery drop, the graded roads' dots, samples and culverts, and the parking spot, so a road change moves them. The host saves each tour's key (its stop names) beside its index, so a save made for another list of stops starts the tour over ([learner driving](mechanics/learner-driving.md)). The flatbed stays the snapshot's `truck`, because cargo, riding the bed and the ferry repair depend on it. The learner vehicles live in `vehicles`, keyed by ID, and a seated player's `vehicle` names the one they occupy; a truck seat without it is the flatbed. They step in the same physics world as the flatbed and crates, so they collide with both, and walking crew treat them as solid boxes. A new vehicle that needs cargo or equipment should follow the same pattern: an ID, a seat on that ID, and its own state beside the pose. Verify the flatbed's suspension, braking, and cargo behavior before adding the fire truck's equipment.

### Interactions

An **E** interaction has an action ID, an optional subject such as an item or farm plot, a key and label for the prompt, a name for the tooltip, and an optional point the reticle can aim at. The feature's browser-safe module owns its action IDs, which choices require explicit selection, and its prompt rules. Its host module supplies a typed handler for each of those IDs.

[Interaction options](../src/interaction-options.ts) combines the feature policies and lists prompts in priority order. Preserve that order when adding a feature because the prompt and reticle both use it. The client sends the selected interaction. The [host dispatcher](../server/interactions.ts) rebuilds the list from current state, checks the exact action and subject, and calls the feature handler. Requests without a choice use the first eligible default action. Field inspections check the exact target in their host handler so the player receives feedback when it goes out of reach. The [host interaction setup](../server/game-interactions.ts) assembles the handler maps, and TypeScript checks that every registered action has a handler. Both registries combine the feature tables with `mergeDisjoint`, which stops the game from loading if two features declare the same action ID, so one feature cannot silently replace another's policy or handler. [Interaction priority tests](../test/interaction-priority.test.mjs) pin the prompt that wins where a repair step competes with setting down a held item.

A new feature's browser-safe interaction module belongs under `src/interactions/`. If it has to live elsewhere, add it to `sharedInteractionFiles` in [`eslint.config.mjs`](../eslint.config.mjs) so the boundary rules keep presentation code out of it.

### Residents

A [resident definition](../src/residents/definition.ts) combines traits the same way a vehicle does. Identity and appearance dress a crew rig. A schedule gives a home, a workplace, hours, a walking pace and a route. A conversation turns the shared snapshot and the crew's trust tier into a greeting and a piece of advice. A list of favors names what the resident asks of the crew, as goods, cargo, checked work finished by reporting back, or a custom job like Wren's gate. Optional remarks add the resident's own small talk. The [remark system](../src/residents/remarks.ts) mixes them with the island's shared remarks and picks one that fits the moment.

| Responsibility | Where it lives |
| --- | --- |
| Definition | One file per resident in [`src/worlds/starter/residents/`](../src/worlds/starter/residents), listed in the island's [registry](../src/worlds/starter/residents.ts). The registry index is each resident's interaction subject. |
| Behavior | [Schedules](../src/residents/schedule.ts) place a resident from the island clock, so every client and the host agree. [Favors](../src/residents/favors.ts) decide what a resident is asking, and [resident interactions](../src/residents/interactions.ts) add **Talk**, **Agree to help** and the hand-in to the shared interaction list. |
| Instance state | The host keeps one [record](../src/residents/trust.ts) per resident in the snapshot and the save: trust, kept favors, the favor under way, the last finding on checked work, and any broken promise. [Host residents](../server/residents.ts) accept, credit each favor once through `keepFavor`, and keep a crate in the yard for a cargo favor. |
| Appearance and placement | The [resident scene](../src/resident-scene.ts) builds and poses one rig per definition, marks cargo bays, and gives the place labels their names. The world layer chooses homes, stops and bays. |

To add a villager, write a definition file and append it to the registry. A visitor arriving by ferry can use the same traits once the ferry runs. A save made before the resident existed loads them as a stranger. Walk the route with the Workbench's **Resident routines** study and the walkability test in [the resident tests](../test/game-residents.test.mjs). See [Residents and favors](mechanics/resident-favors.md) for the playable rules.

### Animals and plants

- **Animals.** In [Juniper Hollow](../src/juniper-habitat.ts), hares and foxes can share locomotion and [obstacle navigation](../src/biome-navigation.ts) with different speeds and clearances. A hare's threat response can send it toward cover, while a fox can give a nearby player space and then resume its patrol. Position and current behavior belong to each animal.
- **Plants.** A habitat trait can guide where an island places reeds or clover. A regrowth trait can let clover replenish forage after grazing, with the patch's remaining forage tracked by the [biome simulation](../src/biome-model.ts). Wind sway can stay in presentation when it only affects appearance. The [Highwood species generator](highwood-species.md#how-the-generator-is-built) bakes trees and shrubs into templates for thin instancing, with near and far tiers, host-safe collision from `treeCollision`, and a sway weight in vertex alpha.

### Terrain and coast

Starter Island's north-west, Highwood, is a baked height field. The [design note](design/island-generation.md) explains why and lists the measured results; this section follows the data.

- **The asset.** [`src/assets/geometry/highwood-heightmap.ts`](../src/assets/geometry/highwood-heightmap.ts) holds base64 heights every 2 m, sand, rock, moisture and shore layers every 4 m, and the reach: the distance from the island's centre to the farthest shore at each coast angle. [`scripts/generate-island.mjs`](../scripts/generate-island.mjs) writes it (`npm run island:generate`) from the parameters in [`src/worlds/starter/layout/island-generation.ts`](../src/worlds/starter/layout/island-generation.ts). Never edit it by hand.
- **Stale bakes.** The asset records a `sourceHash` of every file listed in `bakeSources` in [`bake-sources.ts`](../src/worlds/starter/generation/bake-sources.ts): the generator, its parameters and the authored terrain in [`src/natural-ground.ts`](../src/natural-ground.ts), which holds no roads. [`test/highwood-terrain.test.mjs`](../test/highwood-terrain.test.mjs) fails until the island is baked again. The asset must stay under the 500 KB pre-commit file limit.
- **Who owns the join.** The generated land meets the authored island across the sector from bearing 86° to 165°. The bake owns the join: the higher of the authored and generated ground wins. At runtime, `naturalGroundHeight` in [`src/natural-ground.ts`](../src/natural-ground.ts) uses the baked height beyond protected ground, and blends to the exact authored ground only in the last tenth of the join's fade. `groundHeight` in [`src/terrain.ts`](../src/terrain.ts) adds the graded roads to it.
- **Who reads it.**
  - Walking, scenery placement and the camera sample `groundHeight`. `coastalSurface` mixes the baked sand and rock layers into the beach surface.
  - `coastPoint(angle)` stays a radius per bearing, for bounds and the skiff buoys. On Highwood it reads the baked reach, so it gives the farthest shore along the ray.
  - Host physics builds a Cannon heightfield in [`src/simulation/cargo.ts`](../src/simulation/cargo.ts). It pads the east edge with open sea until the field is at least as wide as it is long, because cannon-es clamps both ray-test index ranges to the heightfield's first dimension. Without the padding, wheel raycasts miss the far rows.
  - The map paints its land raster from `groundHeight` in [`src/island-map.ts`](../src/island-map.ts), so coves, straits and islets show.
  - [`src/shoreline.ts`](../src/shoreline.ts) traces the real shoreline once at load by marching squares, as ordered loops. The surf in [`src/audio/shore.ts`](../src/audio/shore.ts) slides along those loops by distance with the listener.
  - The landscape tints wet ground from the baked moisture layer.
- **Saves made before Highwood.** Old north-west water is now land, and saves load without migration:
  - A saved crewmate inside the skiff buoys resumes there, and the normal movement step handles the changed depth, so a swimmer over new ground stands on it. One beyond the buoys respawns.
  - A saved skiff whose hull is no longer afloat resets to its start (`restoreSkiff` in `server/skiff.ts`).
  - Crates go back into physics as saved. The physics step returns any crate in deep water, or below the recovery depth, to its start.
  - Loose gear saved below ground that has since risen is lifted back onto it. On Highwood, gear saved more than 0.25 m above ground that has since dropped (under a road cut or the reshaped Cairn) settles back down; elsewhere gear may rest on a dock or a crate, so it is left alone. Gear that is held, stowed or on a vehicle bed is never moved. Restored gear is set at its resting height on the ground or water (`restoreItems` in [`server/island-state.ts`](../server/island-state.ts), `restingHeight` in [`server/items.ts`](../server/items.ts); tested by `test/game-restore-ground.test.mjs`).

### Graded roads

Roads shape the ground itself, so physics, wheels, walking, footsteps, the map and the planting all see them. The [road designer](workbench.md#design-roads) edits them. The [forest roads](field-guide/practices/forest-roads.md) entry explains the real-world practice, and the [graded roads craft page](craft/graded-roads.md) explains the techniques and what failed on the way.

- **The data.** [`src/worlds/starter/layout/roads.ts`](../src/worlds/starter/layout/roads.ts) lists each graded road's dots, a bend per stretch (metres its middle is pushed sideways, + left of travel) and optional per-stretch grade limits. The Workbench writes it; hand edits are overwritten on the next save. The village's paved roads are authored in [`src/paved-roads.ts`](../src/paved-roads.ts). Road kinds (width, shoulder, grade limit, turning radius, batter slopes, crown) and the grading's settings are in [`road-kinds.ts`](../src/assets/geometry/road-kinds.ts).
- **One network.** [`src/road-network.ts`](../src/road-network.ts) lists the paved roads, then the graded roads in file order. A road whose end lies on an earlier road's carriageway (plus 0.5 m) joins it there; the earlier road is its host. Highwood has four graded roads: the fire road leaves the harbor road at the trailhead, the Cairn Summit spur and the Pine Draw road leave the fire road, and the Cairn ridge road runs from the Pine Draw road to the spur. A branch must leave its road at 30° or more: a shallower one slides along inside the host's formation, and a test refuses it.
- **The centreline.** [`src/road-shape.ts`](../src/road-shape.ts) puts a hidden knot in the middle of each stretch, moved sideways by its bend, and runs a chord-length Catmull-Rom spline through the dots and those knots. A bend moves a stretch's middle by exactly its value. Samples are 1 m apart.
- **The profile.** [`src/road-profile.ts`](../src/road-profile.ts) starts from the ground averaged across the road and smoothed over 20 m. It holds the road to its grade limit with forward and backward passes, smoothing a little between them. A branch's joining end is held at its host's surface; a free end is not pinned, so a road ending on a peak keeps its grade instead of jumping to the summit. On steep side slopes the road benches into the hill, blending in from a side slope of 0.45 to fully benched at 0.75, so no fill hangs off the downhill side.
- **Banks.** [`src/road-banks.ts`](../src/road-banks.ts) gives each side of each sample its bank slopes: cuts at 1 horizontal : 1 vertical and fills at 1.5 horizontal : 1 vertical (about 34°, see [conventions](conventions.md#space)). A cut that would not meet the ground within 18 m is steepened in steps, as far as a rock cut at 0.25 : 1 (about 76°), so no bank ends in a wall. A fill tries only 1.5 : 1, because loose spoil can't stand like rock; one that can't meet the ground is a designer warning, graded at the rock-cut batter until the road is moved. No shipped road has one. Where even that fails the designer warns.
- **Cut and fill.** [`src/road-grading.ts`](../src/road-grading.ts) solves the network as a whole. For each point it gathers a candidate from every stretch of road nearby, one per switchback leg ([`src/road-index.ts`](../src/road-index.ts)). A branch's mouth warps from its host's surface to its own over 8 m, and a smooth union over 8 m rounds the junction's corners into a bell-mouth. Inside any road's formation, the earliest road in the network wins, so a branch never moves its host (a test allows 2 cm). Elsewhere the ground is the lowest of the cuts above it and the highest of the fills below it, each bank counting only out to where it meets the ground. The result is a raster of height changes in 1 m cells, in 16 m tiles. It is built whole on the first ground lookup, only for the tiles a road reaches; elsewhere the change is zero.
- **Culverts.** [`src/road-culverts.ts`](../src/road-culverts.ts) floods rain over a 1 m lattice round the roads, on the natural and on the graded ground, and gives a culvert to every basin where the grading deepens a pond by more than 3 cm. Its outlet is where the natural ground, followed downhill, leaves the earthworks with at least a 1% fall for the pipe. Highwood's roads need 19, drawn by [`culverts.ts`](../src/assets/culverts.ts). A test traces rain over the same lattice, letting water that reaches an inlet carry on from its outlet, and checks that every trace reaching the sea over the natural ground still does.
- **Where the code lives.** Three modules, in one direction, with no import cycle:
  - [`src/natural-ground.ts`](../src/natural-ground.ts): the coast, the authored south, Highwood's baked heights and `naturalGroundHeight`. The terrain bake reads only this.
  - [`src/roads.ts`](../src/roads.ts): the grading of the roads in `roads.ts` (or of a previewed draft), its bake, and every road query: `roadDelta`, `gradedRoads`, `roadSurfaceSource`, `roadCulverts`, `roadClearance`, `roadEarthworks`, `underGradedRoad` and `roadFormation`. It also keeps the reset registry (`onRoadsChange`).
  - [`src/terrain.ts`](../src/terrain.ts): `groundHeight` (natural ground plus `roadDelta`), the shore surface, water depth and walking height. It re-exports the natural ground, so older imports still work.
  - [`src/road-surface-at.ts`](../src/road-surface-at.ts) holds `roadSurfaceAt`, which only footsteps and wildlife read, so a change to how a road sounds underfoot is not a source of any bake.
- **The ground contract.** `groundHeight` is `naturalGroundHeight` plus the road layer. Use `naturalGroundHeight` for anything about the land before roads: the bake, its seam and drainage tests, Suggest route. `roadClearance(point)` gives the distance to the nearest road's formation edge, negative on the road; trees, grass and the planting bake read it. `roadEarthworks(point)` gives how far the grading moved the ground; Highwood's trees, logs and granite outcrops keep off anything moved more than `highwoodEarthworksM`, through `clearOfEarthworks` in [`highwood-clearings.ts`](../src/worlds/starter/highwood-clearings.ts), so none stands on a cut or fill bank, while understory may. `roadSurfaceAt(point)` says what a foot lands on: `asphalt` within a paved junction's apron, out to the formation edge as the surface draws it, `earth` on a carriageway, `verge` on a graded road's shoulder out to the formation edge (a paved road's own shoulder is not one), or nothing. Footsteps play asphalt as pavement, the carriageway as gravel and the verge as bare ground, so the crunch stops at the road's edge and at its end.
- **The road bake.** [`scripts/bake-roads.mjs`](../scripts/bake-roads.mjs) (`npm run island:roads`) grades the roads in the source tree once and writes [`src/assets/geometry/road-layer.ts`](../src/assets/geometry/road-layer.ts), about 380 KB:
  - the raster's 159 tiles as float32, exactly as graded, so the baked ground is bit for bit the live one;
  - the 18 culverts, with full-precision numbers;
  - the formation distance on the terrain tiles' 1 m grid, in 177 tiles of int16 steps of 5 mm, with a "far" value where no road is near. The generated terrain tiles' vertices all stand on that grid, so clipping them reads the bake. Off the grid, as at the authored island's ring of vertices, `roadFormation` asks the grading: blending the grid between nodes is not safe, because the distance jumps where one road's say gives way to another's, by up to 0.9 m within two metres of an edge.

  [`src/baked-roads.ts`](../src/baked-roads.ts) decodes it on the first road query. `roadDelta`, the raster's `near` test, `roadEarthworks`, `roadCulverts` and `roadFormation` read the bake, so the live raster is never built on load. The grading's profiles are still built, lazily, for `roadClearance`, the road surface's fields and footsteps. The bake records a `layoutKey`, a fingerprint of the roads, the paved roads, the road kinds, the network and drainage settings, and the heightmap's hash (not the grading code: an edit to that is caught by the `sourceHash` test, not at runtime); if the source tree's roads no longer match it (just after a Workbench save, say), the game grades them live and warns in the console until the bake is run again.
- **Previews.** `previewRoadLayouts` grades a draft live, and every memo built from the roads forgets itself through `onRoadsChange`: the granite rocks and the summit pad they keep clear of, the walking solids, the standing plants, the old island's trees and rocks (`islandTrees()`, `islandRocks()`) and the northern regions' props (`northernProps()`). Ground heights read once for fixed sites (the Fire Watch's base, the market awning, the lichen rock) are not reset; no road runs under them. Previewing the source tree's roads again, as closing the designer does, goes back to the bake. `test/road-layer.test.mjs` lays a draft road through a tree and checks it goes from the forest and the solids, and comes back.
- **Load cost.** Measured in the Landscape Workbench on an M1 Pro (`focus=-310,331`), before the road bake and after it:

  | Step | Before | After |
  | --- | --- | --- |
  | `createIslandTerrain` | 1.9 s | 1.7 s |
  | Road surface mesh (`createRoads`) | 376 ms | about 330 ms |
  | Culverts, after the first frame | 227 ms | 6 ms |
  | Forest | 343 ms | 345 ms |
  | Granite outcrops | 30 ms | 58 ms |
  | The world in all, culverts aside | 3.37 s | 3.1 s |

  The terrain saves the live raster (about 140 ms) and the formation distance at the generated tiles' vertices; the authored ring's vertices near roads still ask the grading, about 90 ms with the profiles. The granite rocks are now placed when they are first drawn rather than when the walking solids load, so their time moved into the table, not up. The road surface mesh is not baked: its 79,874 vertices and 266,598 indices come to about 4.3 MB as float32, 5.7 MB as base64, over the 500 KB pre-commit file limit and far over the 1 MB a bake should add to the main chunk; loading it as a separate file built at build time is the way out ([#285](https://github.com/brylie/mission-island/issues/285)). The road layer adds 388 KB to the shared `effect-props` chunk (133 KB gzipped). A `groundHeight` call costs about a fifth to a third more than `naturalGroundHeight`, tens of nanoseconds.
- **Baking.** The bakes chain their hashes. `roadSources` in [`bake-sources.ts`](../src/worlds/starter/generation/bake-sources.ts) lists the road files, the natural ground and the baked heightmap, so a terrain rebake makes the road bake stale; `plantingSources` lists `road-layer.ts`, so a road rebake makes the planting stale. `npm run island:generate` runs the heightmap, then the roads, then the planting; `npm run island:roads` runs the roads, then the planting. `test/road-layer.test.mjs` fails on a stale road bake and checks the bake against a live grading: every raster tile and points between nodes exactly, the culverts exactly, and the formation distance at every grid node near a road within half a step. Footsteps (`road-surface-at.ts`) are no bake's source; `terrain.ts` is a planting source only, because the planter reads `groundHeight`.
- **Drawing.** [`src/assets/road-network-mesh.ts`](../src/assets/road-network-mesh.ts) builds one mesh over every road's formation, paved and graded, on a 0.5 m grid clipped to the formation field, with shared vertices, so the network has no seams or overlaps; a short skirt hangs from its outline. A paved road's free end stops square. Each vertex carries signed distances to the carriageway, the paved carriageways and the graded formations, and [`src/road-material.ts`](../src/road-material.ts) turns them into asphalt, gravel shoulder, earth with ruts, and verge. The terrain is cut to the roads' outline (`clipOutsideRoads`, from `roadFormation` in `roads.ts`, read from the road bake on the generated tiles), a quarter metre inside it, so its edge sits under the road at its true height and neither pokes through nor dips beside it. [`src/assets/culverts.ts`](../src/assets/culverts.ts) draws each culvert after the first frame: a headwall or, for an inlet in a cut, a drop inlet; and at the fill's toe an outlet headwall with a riprap apron. [`src/island-map.ts`](../src/island-map.ts) draws the roads on the map as a pale fill (#dcbf8a) on a dark edge (#3b2f1c), at least 3:1 on every land colour (`test/island-map-look.test.mjs`). The host's physics heightfield samples `groundHeight` every metre (`src/simulation/cargo.ts`), so wheels ride the graded surface.
- **Not modelled yet.** Ditches, rolling dips and running water. Fords, fallen logs and vehicle colliders for trees along the road come with the rest of Phase 3.

**Workbench save endpoint.** [`server/workbench-save.ts`](../server/workbench-save.ts) is a Vite plugin that runs only on the development server (`apply: 'serve'`). It accepts `POST /__workbench/roads` and writes exactly one file, `roads.ts`, from validated JSON. The schema, `readRoadLayouts` and `roadsSource`, lives in [`src/road-layout-source.ts`](../src/road-layout-source.ts), which the designer also uses to check a draft before sending it. The server writes `roads.ts` atomically, to a temporary file beside it that is then renamed over it, so Vite and the bakes never read half a file. The schema allows at most 32 roads, graded kinds only (a paved kind, or a name such as `toString`, is refused), and finite coordinates; the server reads at most 256 KB. Errors name a road by its name. Four checks keep other senders out. The request must come from a loopback address, so other computers on the network are refused. It must carry the custom header `x-mission-island-workbench: save`, which makes a browser send a CORS preflight. That header is not enough on its own, because in Vite 8 the dev CORS middleware, and then its host check, run before plugin middleware, and the CORS middleware grants preflights to any page served from localhost. So the request must also come from the Workbench page itself: its `Origin` must be `http://` or `https://` plus the request's `Host`, or the browser must mark it `Sec-Fetch-Site: same-origin`. A browser sets both headers itself and no page can change them. The `Host` must also be a loopback name (`localhost`, `127.0.0.1` or `[::1]`): a page on another domain whose DNS was rebound to 127.0.0.1 is same-origin with itself, so the Host check is what refuses it. Vite's own host check would too, but only while `vite.config.ts` leaves `allowedHosts` and `https` unset. The route, header and rounding live in [`src/workbench-save-contract.ts`](../src/workbench-save-contract.ts), shared by the server and the designer. `roads.ts` is authored data and may not import, so the generator writes its `kind` union out from `gradedRoadKinds` at each save, and the type check catches a checked-in file that has fallen behind. Because `roads.ts` reaches `vite.config.ts` through `server/game.ts` and `src/roads.ts`, a save restarts the dev server; the designer keeps its save notice in session storage so it survives the reload. The designer's draft stores a hash of the `roads.ts` it began from and warns before a save would overwrite a newer one.

**Playtest mark endpoint.** [`server/playtest-marks.ts`](../server/playtest-marks.ts) saves [playtest marks](iteration-tooling.md#playtest-marks). `server/multiplayer.ts` mounts it at `POST /api/playtest-mark` on the development server only, never on `vite preview`. Its trust model differs from the Workbench save. Marks are meant to come from a second computer on the LAN too, so the endpoint does not check for a loopback address. It accepts a request carrying the bearer token of a crewmate who has joined the host, as `/api/playtest-event` does. A browser page on another site cannot read or send that token, but the client picks its own token, so anyone who can reach the port and join can save. What the endpoint protects is the disk. The server picks every path: a timestamp plus a slug of `[a-z0-9-]`, inside `playtest-notes/` or `MISSION_ISLAND_NOTES_DIR`. It reads at most 8 MB, accepts only a base64 JPEG and two notes of up to 2,000 characters, and keeps only the known record fields. `vite.config.ts` keeps `playtest-notes/` out of both the served files and the file watcher, so a LAN player cannot download another tester's marks and a save never reloads the page. The contract (route, limits, validation, folder names) lives in [`src/playtest-mark.ts`](../src/playtest-mark.ts), shared by the server, the game page and the tests. Marks also rely on a contract in [`src/island-meshes.ts`](../src/island-meshes.ts): each merged scenery batch carries `metadata.mergedFrom`, its source parts in merge order with their triangle counts, so a picked triangle maps back to its part. A change to how scenery is merged must keep that list in step.

### Highwood forest

Highwood's plants are baked at generation time, like the height field. The [backcountry page](backcountry.md#forest) explains the planting and its numbers; this section follows the data and the contracts.

- **The bake.** [`scripts/plant-highwood.mjs`](../scripts/plant-highwood.mjs) writes [`src/assets/geometry/highwood-plants.ts`](../src/assets/geometry/highwood-plants.ts) during `npm run island:generate` or `npm run island:roads`. Each plant takes 8 bytes: position, species, a packed byte for layer, age, exposure and variant, heading and scale. An 8 m ground raster beside it holds needle litter, heath, moss and bracken. Never edit it by hand.
- **Stale bakes.** The asset records a `sourceHash` of every file in `plantingSources` in [`bake-sources.ts`](../src/worlds/starter/generation/bake-sources.ts), and [`test/highwood-habitat.test.mjs`](../test/highwood-habitat.test.mjs) fails until the forest is baked again.
- **Decoding.** [`src/worlds/starter/highwood-planting.ts`](../src/worlds/starter/highwood-planting.ts) decodes the bake once.
- **One planting filter.** `plantFits(point, layer)` in [`highwood-clearings.ts`](../src/worlds/starter/highwood-clearings.ts) is the one test of whether a plant may stand beside the roads: off routes and graded roads by the planting clearance, trees and deadwood off the road banks, ground cover off banks too steep to green over. The bake keeps only plants that fit. [`src/highwood-standing.ts`](../src/highwood-standing.ts) gives `standingPlants()`: the baked list as it is while the roads are read from the bake (no shipped plant fails the test), or filtered by `plantFits` while they are graded live: a previewed draft, or roads saved since the last bake. The forest, the walking solids and the granite outcrops' wood grid all read it, so a tree is drawn exactly where it is solid and the rocks keep off it.
- **Plant identity.** The bake's array order is not a stable plant ID: a change to any table can reorder it. A plant is identified by its layer and planting cell. Anything that saves per-plant state, such as a burn scar, should key on (layer, cell).
- **Drawing.** [`src/highwood-forest.ts`](../src/highwood-forest.ts) draws two tiers. Near tiles show detailed templates as thin instances, one batch per template across every near tile. Far tiles are merged meshes, one per 64 m tile and material, culled whole.
- **Walking and wind.** [`src/highwood-solids.ts`](../src/highwood-solids.ts) files the standing trunks, snags and logs in a 4 m grid for walking checks, and canopy crowns in the same grid, on the first walking check and again after the roads change. Wind shelter and crown rustle in [`src/audio/wind-model.ts`](../src/audio/wind-model.ts) read the crown index. Trees add no physics bodies.
- **Granite rocks.** [`src/highwood-outcrops.ts`](../src/highwood-outcrops.ts) places outcrops and clitter live at load (about 50 ms), not baked, so a rebake of the height field moves them. The host's solids and every screen read the one memoised list, placed again after the roads change. They keep clear of the summit spur's turning pad in whichever roads the island has now. `highwood-solids.ts` files each block as a rounded rectangle, with a corner radius of half its half width, whose top leans as the drawn block's does (`rockBlockLean` in `src/granite-blocks.ts`, the first draws of the block's own random stream), and the drawn block stays inside it. Routes and sight lines come from [`src/worlds/starter/highwood-clearings.ts`](../src/worlds/starter/highwood-clearings.ts). The planting bake (`generation/plant-highwood.ts`) reads the same file, `plantFits` and `sightlineAlong`, so a new road or kept-open view reaches the forest and the rocks alike; it is a planting bake source.
- **Ground cover.** The Highwood terrain tiles carry the ground raster as a `groundCover` vertex attribute, read by the ground shader in [`src/beach-material.ts`](../src/beach-material.ts). Bracken is stored inverted, because a mesh without the attribute reads (0, 0, 0, 1); stored straight, that would be full bracken everywhere else.

**Scene fog contract.** [`src/scene-fog.ts`](../src/scene-fog.ts) attaches a material plugin to every standard and PBR material in the scene and replaces Babylon's own fog. It mixes toward the fog colour after image processing, by distance from the eye, so land, trees, buildings and sea at the same distance fade alike ([#219](https://github.com/brylie/mission-island/issues/219)). Because the plugin turns off each material's `fogEnabled`, setting `material.fogEnabled` or `mesh.applyFog` no longer does anything. There is no per-material opt-out yet: every standard and PBR material fogs. Add one to the plugin when a material needs it. Cloning a material keeps its GPU textures but drops any plugin that isn't registered as `BABYLON.<className>`; `SceneFog` is registered, so clones keep the fog.

## Physics cost and static colliders

The cargo world in [cargo.ts](../src/simulation/cargo.ts) holds a few moving bodies, the flatbed, learner vehicles and crates, among hundreds of static ones: tree trunks, rocks, buildings, the heightfield and the dock. It steps twice per host tick. The host, the integration tests and the coverage run all pay for that step, so its cost decides how fast the whole suite runs.

Stock cannon-es grows with the square of the body count in two places on every substep:

- **The sweep.** `SAPBroadphase` sorts bodies along one axis and should stop scanning once the next body starts past the current one. It runs its "can these two collide?" filter before that bound, though. A static body skips every other static body without checking the bound, and stops only at the first moving body past it. Measured on 2026-11-22, with 363 static bodies, one substep made about 27,500 pair checks to find 3 real pairs.
- **Contact memory.** `ArrayCollisionMatrix` keeps one slot for every possible body pair (66,795 for 366 bodies) and zeroes them all each substep. It does this to tell a first contact from a continuing one.

[broadphase.ts](../src/simulation/broadphase.ts) replaces both. `SettledSweepBroadphase` scans only the moving bodies after a static or sleeping one, because two settled bodies can never collide. `SparseCollisionMatrix` remembers only the pairs touching this step. Both keep the stock pair order and index keys, so the solver sees the same input. Like the stock matrix, removing a body forgets the remembered contacts of the highest body indices, so a crate taken off and released again fires a fresh `collide` event. The crate impact sounds listen to `beginContact`, which cannon tracks by body ID, so the matrix does not affect them. The cargo world leaves `allowSleep` off, so in play "settled" means static, or a vehicle that [ground drive](../src/simulation/ground-drive.ts) put to sleep while parked. A crate that hits a parked vehicle wakes it just as in stock cannon-es. The pair still reaches the narrowphase, which wakes a sleeping body when the other body is awake, not static, and moving faster than √2 times its own `sleepSpeedLimit`. The [broadphase tests](../test/broadphase.test.mjs) step a stock world and a replaced world side by side and compare pairs, first-contact events, and positions bit for bit.

The step now costs about the number of moving bodies times the number of static bodies. Adding scenery colliders adds cost linearly. When a new world builds its own cannon `World`, call `useSparseCollisions(world)`. Both classes override cannon-es 0.20 internals (`SAPBroadphase.collisionPairs` and `ArrayCollisionMatrix`). After upgrading cannon-es, run the broadphase tests before anything else.

Coverage instruments every executed line, including cannon-es in `node_modules`, so physics-heavy tests run several times slower under it. Measured on 2026-11-22 on a 10-core laptop: before this change the suite took 58 s under `npm test` and 338 s under `npm run coverage`; after it, 20 s and 76 s.

## Static checks

`npm run quality` runs lint, type checking, tests, unused-code checks, and the build. CI runs the tests once, under the coverage gate (see [Quality checks](../CONTRIBUTING.md#quality-checks)). First-party TypeScript modules have a 350-line file limit, a 140-line function limit, and a cyclomatic complexity ceiling of 24. Line limits exclude comments and blank lines. Test files have the same file limit. The [ESLint config](../eslint.config.mjs) records per-file ceilings for existing hotspots, including modules that grew through formatting. Lower an exception or remove it when the relevant code is split.

Import checks keep browser modules out of `server/`. Host simulation, shared simulation and world data can read the dependency-free definitions in `src/assets/geometry/`. Imports from rendering and transport modules are restricted. Type-only imports are allowed for host command and save contracts. These checks cover direct imports. Review how dependencies flow through a feature when moving code across layers.
